# 验证规范

## 1. 适用范围

以下改动必须验证：

- 运行时行为、业务逻辑或接口行为。
- 构建流程、依赖、配置或环境约束。
- 数据格式、序列化、迁移或兼容性。
- UI 展示、交互、路由或页面状态。

仅修改说明文字、注释、拼写或排版时，可以不运行完整测试，但必须检查变更范围、差异内容、链接与示例，确认没有夹带行为性改动。

## 2. 验证原则

- 优先使用项目已有测试、检查和构建命令。
- 验证范围应覆盖本次改动及其直接影响面；高风险改动再扩大回归范围。
- 项目没有测试体系时，不为单次改动强行引入测试框架；使用最小可运行脚本、命令或明确的手动步骤。
- 修复 bug 时，先用测试或最小步骤复现问题，再修复并验证相关回归。
- 增加校验时，同时覆盖合法输入和非法输入，并核对各自预期行为。
- 重构时，使用相同输入、测试或操作步骤确认重构前后外部行为一致。

## 3. 页面验证

前端自动化测试使用 Vitest、React Testing Library、`@testing-library/user-event`、`@testing-library/jest-dom` 和 jsdom，不使用 Playwright。单元测试与组件测试优先；真实前后端跨栈验收放在项目根目录 `tests/`。

页面改动按以下顺序选择验证方式，并在当前方式不可用时逐级降级：

1. 使用项目已有的测试、检查或验证脚本，核对关键状态与结果。
2. 提供编号清晰的手动验证步骤、测试数据与预期结果。

发生降级时，必须说明上一级方式不可用的原因。仅确认页面能够打开，不等于完成了交互验证。

## 4. 自动化验证命令

- 开发时使用 `npm run test` 进入监听模式。
- CI 使用 `npm run test:run` 单次执行测试。
- 类型检查、ESLint、构建与测试分别执行，具体命令以项目 `package.json` 中已有脚本为准。
- 覆盖率阈值暂不设定，待项目形成稳定测试基线后确认。

## 5. 验证记录与最终汇报

只汇报实际执行过的验证，不得把代码审阅、静态推断或计划执行写成“已验证”。命令失败、环境受限或未运行时，应如实说明结果和原因。

最终汇报至少包含：

- 改动内容与影响范围。
- 实际执行的命令或操作步骤，以及通过或失败结果。
- 未执行的验证、未覆盖范围及原因。
- 仍存在的风险、限制或后续建议；没有时明确说明。
