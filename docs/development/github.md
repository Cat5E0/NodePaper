# GitHub 规范

## 构建与 CI

- 拉取请求必须运行最小检查；合并至 `main` 后运行完整构建。
- 复用项目已有的格式化、静态检查、测试和构建命令，不为 CI 维护重复命令。
- 固定 Node.js、Rust 等运行时版本，依赖安装必须使用锁文件。
- CI 工作流默认最小权限；令牌、签名材料和其他敏感配置只通过 GitHub Secrets 注入，日志不得输出其内容。
- 构建步骤应名称清晰、失败可定位；不提交构建产物、缓存或大型文件。

## 推送与拉取请求

- 禁止直接推送 `main`，所有改动通过拉取请求合并。
- 分支使用 `feat/`、`fix/`、`docs/` 等清晰前缀；Codex 创建的分支使用 `codex/` 前缀。
- 推送前确认暂存内容、目标分支、远程地址，并完成与改动相称的本地验证。
- 推送、强制推送、创建或合并拉取请求、创建标签，均须工程师明确确认。
- 禁止使用 `--force`；确需整理历史时，先说明影响并取得确认。
- 拉取请求应说明改动范围、验证结果、未覆盖项和风险；无关重构不得与功能改动混合。
- `main` 应启用分支保护，要求 CI 通过并至少保留一次人工审阅；默认使用 squash merge。

## 发行与回滚

- 版本遵循语义化版本：不兼容改动升主版本，新功能升次版本，修复升修订版本。
- 仅从受保护的 `main` 发行，并以明确标签标识版本，例如 `v0.1.0`。
- 发行前必须确认 CI 通过、版本号一致、变更日志更新、关键功能验证完成，以及依赖和敏感信息检查无误。
- Release 说明应包含新增、修复、破坏性变更、升级或回退说明和已知限制。
- 正式制品仅由 CI 生成并作为 GitHub Release 附件发布；不从个人本地直接上传正式制品。
- `v0.2.0-beta.1`、`v0.2.0-rc.1` 等预发布版本须标记为预发布，稳定版本才作为正式 Release。
- 保留旧版本标签与制品。发现严重问题时，撤回或标记问题版本，并指明可用的安全版本；不得改写已发布版本历史。
- 创建 Release、上传制品和任何对外发行操作，均须工程师明确确认。令牌、证书、私钥及更新服务密钥不得写入仓库、Issue、拉取请求或日志。
