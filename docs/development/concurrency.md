# 并发与线程规范

## 基本原则

- 并发是多个任务交替推进，并行是多个任务同时执行；异步用于等待期间让出执行权，不等同于多线程。
- 默认使用单线程顺序执行；仅在任务存在可验证的响应性或吞吐问题时引入并发。
- I/O 密集任务优先使用异步或受控并发；CPU 密集任务仅在测量确认收益后使用并行。
- 不因“充分利用资源”强制脚本或业务代码使用多线程，也不为一次性短任务增加并发复杂度。

## 选择顺序

按以下顺序选择最简单且满足要求的方案：

1. 单线程同步执行：适用于短任务、顺序敏感流程和数据量较小的处理。
2. 异步或受控并发：适用于网络、文件、数据库等等待时间占主导的任务。
3. 多线程或多进程并行：适用于可独立拆分、CPU 占用明显且基准测试证明有收益的任务。

- 任务之间存在强顺序、共享状态频繁或工作量不足时，不使用并行。
- 引入并发前应明确目标指标；实现后比较耗时、吞吐、资源占用和复杂度变化。

## 资源与背压

- 线程数、同时运行的任务数、队列容量和重试次数必须有上限，不得随输入规模无限增长。
- 并发上限根据任务性质、运行环境和测量结果确定，不在通用代码中武断固定为 CPU 核心数或其他常量。
- 生产速度可能超过消费速度时必须设计背压，可采用有界队列、并发限制、批处理或拒绝策略。
- 不得为每条数据创建独立线程；优先复用运行时、线程池或受控任务集合。

## 状态与同步

- 优先使用不可变数据、所有权转移和消息传递，减少共享可变状态。
- 必须共享状态时，锁定范围保持最小，不在锁内执行阻塞 I/O、长计算或未知外部调用。
- 不得跨 `await` 持锁；需要多个锁时规定统一获取顺序，避免死锁。
- 不依赖任务完成的偶然顺序；需要顺序时使用序号、单一消费者或明确的排序阶段。
- 共享状态的读写边界、线程安全假设和生命周期必须在接口或必要注释中说明。

## 生命周期与错误处理

- 长任务按业务需要支持超时和取消，并明确取消后哪些结果可以丢弃、哪些资源必须释放。
- 子任务错误必须传播、汇总或被明确处理，不得静默丢失，也不得让后台任务脱离管理。
- 应用关闭、页面卸载或父任务结束时，停止接收新任务，并等待或取消已有任务后回收线程、句柄和连接。
- 重试必须有上限，并区分可重试错误与永久错误；并发重试不得放大外部系统压力。

## 前端

- React 渲染、状态更新和交互编排保留在 UI 主线程，并避免在一次事件处理中执行长计算。
- I/O 使用浏览器异步 API；不得为普通请求或状态管理引入 Web Worker。
- 仅当性能测量确认 CPU 计算阻塞交互时使用 Web Worker，并定义可序列化的消息协议、错误处理、取消和销毁流程。
- Worker 不直接持有组件状态；组件卸载或功能退出时必须终止不再需要的任务。

## Rust 与 Tauri

- 同步 command 仅执行短时、非阻塞工作；I/O 使用异步 command。
- 阻塞 I/O 和 CPU 密集计算必须与异步运行时及 UI 线程隔离，使用受控的阻塞任务、线程池或工作线程。
- 跨任务通信优先使用具有明确容量和关闭语义的 channel；共享状态遵循最小锁范围。
- 不得擅自引入 Rayon 等并行计算依赖；只有现有方案不能满足经测量的目标时再讨论选型。
- Tauri 应用正常退出时必须取消或回收后台任务；进程重启后不得假定线程、任务或内存状态仍然保留。

## Python

- I/O 密集任务可使用线程或异步；CPU 密集任务优先评估多进程，并通过基准测试确认收益。
- 简短脚本和顺序敏感任务默认单线程，不强制并发。
- Windows 使用多进程时，进程入口必须置于 `if __name__ == "__main__":` 保护下。
- 线程池或进程池必须显式关闭；任务参数和返回值应可安全传递，避免依赖隐式全局可变状态。

## 可观测性

- 长任务记录任务标识、阶段、耗时、结果和取消原因，必要时记录队列长度或并发占用。
- 日志应能区分超时、主动取消、资源受限和实际失败，但不得记录密钥、隐私数据或未经脱敏的任务内容。
- 高频任务的日志应受级别或采样控制，避免日志本身成为性能瓶颈。

## 测试与验证

- 并发逻辑至少覆盖正常完成、错误传播、超时、取消和关闭回收。
- 根据功能风险测试竞态、乱序、重复执行、队列满载和部分任务失败。
- 测试不得依赖固定睡眠或偶然调度顺序；优先使用可控信号、屏障、模拟时钟或确定性输入。
- 对吞吐或响应性作出承诺时，使用接近实际负载的压力测试或基准测试，并记录环境与并发配置。
- 验证结束后确认无遗留线程、任务、锁、进程或未消费队列。
