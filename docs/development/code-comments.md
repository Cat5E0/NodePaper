# 代码注释规范

## 1. 基本原则

- 注释用于解释代码背后的原因、约束、风险和取舍，不逐行翻译实现。
- 优先使用准确命名、清晰类型和职责拆分让代码自解释；能通过代码表达的内容不写成注释。
- 注释应简短、紧邻所描述的代码，并使用与项目一致的术语。
- 不要求为每个文件、符号或代码块添加注释。

## 2. 必须说明的内容

以下信息无法从代码直接得出时，必须添加注释：

- 公共 API 的用途、输入输出、错误和副作用。
- 非直观的业务约束、边界条件与兼容性处理。
- 安全、并发、生命周期和性能方面的重要不变量。
- 算法或公式的选择依据；引用外部资料时提供稳定来源。
- 数值的单位、范围、坐标系、时区或精度要求。

```ts
// 服务端时间用于避免本机时钟偏差导致令牌被提前判定过期。
const expiresAt = issuedAt + expiresIn;
```

```ts
// 错误：令牌过期时间。
const expiresAt = issuedAt + expiresIn;
```

## 3. 禁止事项

- 禁止描述显而易见的语句、逐行复述代码或重复类型信息。
- 禁止使用作者、日期和修改过程组成流水账；历史信息交由 Git 保存。
- 禁止保留大段被注释掉的代码，需要时从版本历史恢复。
- 禁止保留与当前实现不一致、已经失效或无法核实的注释。
- 禁止在注释、示例和文档字符串中记录密钥、令牌、个人信息或内部敏感数据。

## 4. TODO 与 FIXME

- `TODO` 表示已知但尚未实施的改进，`FIXME` 表示已确认且需要修正的问题。
- 必须写明原因以及可执行的完成条件；存在真实工单时可以附上编号，不得虚构编号。
- 临时绕过方案应说明移除条件，不使用“以后优化”等无执行依据的表述。

```ts
// TODO: 后端支持批量接口后合并请求，以一次响应替代当前逐项查询。
```

```rust
// FIXME: Windows 文件锁可能使原子替换失败；改为关闭句柄后重试。
```

## 5. 语言约定

### TypeScript 与 React

- 仅为公共接口和复杂契约编写 TSDoc/JSDoc，不为私有实现机械补全文档块。
- Hook 的副作用、依赖取舍或刻意省略依赖必须说明原因；注释不能代替正确的依赖声明。

### Rust

- 公共项使用 `///`，需要说明模块整体职责时使用 `//!`。
- 每个 `unsafe` 块必须使用 `SAFETY:` 说明调用方保证、已验证条件和所依赖的不变量。

```rust
// SAFETY: 指针来自同一缓冲区，且 length 已验证不超过其已初始化区域。
let bytes = unsafe { std::slice::from_raw_parts(pointer, length) };
```

### Python

- 公共模块、类和函数使用 docstring 描述契约，格式服从项目已有风格。
- 简单私有函数无需重复签名和类型标注。

### C 与 C++

- 仅当项目已经启用 Doxygen 时，公共接口沿用 Doxygen 风格。
- 私有实现仍遵循“少而必要”，不为生成文档强制添加空洞注释。

## 6. 维护与评审

- 修改行为、契约或约束时，必须同步更新相关注释；无法保持准确的注释应删除或重写。
- 评审时检查注释是否必要、准确、可验证，是否解释了代码本身无法表达的信息。
- 注释指出风险或不变量时，评审应同时确认实现和测试确实维护该约束。
